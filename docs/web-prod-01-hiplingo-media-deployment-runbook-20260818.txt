Host:   web-prod-01
Public site: https://hiplingo.com/
Public media URL prefix: https://hiplingo.com/media/

PURPOSE
-------
This runbook describes the complete Hiplingo public-media publication and
deployment path from metadata-editor to the production server.

It is intentionally separate from Hiplingo frontend deployment,
nathanbrenton.com deployment, and the private metadata-editor media-library.

Core safety rule:

    media-library/        PRIVATE — NEVER DEPLOY
    published-media/      SANITIZED PUBLIC PACKAGE — MAY DEPLOY

The production media tree is persistent and has an independent lifecycle from
the Hiplingo frontend. Rolling the frontend forward/back must not erase or
roll back published-media.

------------

        NEVER copied to the public server

    public URL:
      https://hiplingo.com/media/catalog.json


DEPLOYMENT IDENTITIES / WRITE BOUNDARIES
----------------------------------------

Media deployment user:
    deploy-hiplingo-media

Primary group:
    hiplingo-media-deploy

Frontend deployment user:
    deploy-hiplingo-app

Frontend group:
    hiplingo-app-deploy

nginx:
    www-data
    read-only
    NOT a member of either deployment group


WHY /var/www/hiplingo.com IS MODE 3775
---------------------------------------
metadata-editor does not rsync directly into the live directory. It stages a
new tree beside it, verifies the staged content, then performs an atomic swap.

Temporary path shape:

    /var/www/hiplingo.com/
      published-media
      published-media.metadata-editor-incoming.<operation-id>

The media deployment identity therefore needs permission to CREATE A SIBLING
under /var/www/hiplingo.com.

Current production parent:

    /var/www/hiplingo.com
        owner root
        group hiplingo-media-deploy
        mode 3775
        drwxrwsr-t

Mode meaning:

    SGID (2xxx)
        new entries inherit hiplingo-media-deploy

    sticky bit (1xxx)
        a group member cannot rename/remove a root-owned sibling such as app

    group write (0775 portion)
        allows deploy-hiplingo-media to create atomic incoming/backup paths

The frontend remains:

    /var/www/hiplingo.com/app
        root:hiplingo-app-deploy
        mode 2775

Do NOT use chmod 777.
Do NOT add www-data to hiplingo-media-deploy.


PUBLIC FILE-MODE CONTRACT
-------------------------

Private Library content and public web content intentionally differ.

Private Library waveform:

    waveform-peaks.wfp
        0600 is acceptable/private

Public package / production:

    directories
        0755

    files
        0644

    waveform-peaks.wfp
        0644

Why:
    nginx/www-data is deliberately outside the deploy group, so public assets
    must be readable/traversable without granting nginx deployment privileges.

Defense in depth implemented in metadata-editor:

    publication boundary:
        copied public assets are chmod 0644

    deployment boundary:
        rsync enforces
            directories 0755
            files       0644

The first production deployment found WFP files at 0600. nginx consequently
returned HTTP 403 for those assets. This is why both boundaries now normalize
permissions.

6. PUBLIC SERVER — REQUIRED FILESYSTEM PERMISSIONS
======================================================================

Run on: PUBLIC SERVER as n8
Output: SAFE TO PASTE.

Current intended boundary:

    sudo chgrp hiplingo-media-deploy /var/www/hiplingo.com
    sudo chmod 3775 /var/www/hiplingo.com

For a freshly created EMPTY live media directory before the first deployment:

    sudo chown deploy-hiplingo-media:hiplingo-media-deploy \
      /var/www/hiplingo.com/published-media

    sudo chmod 2775 \
      /var/www/hiplingo.com/published-media

Why the initial directory is owned by the deploy user:
    the sticky parent prevents a group member from renaming a root-owned child.

After the first atomic deployment, the live directory is expected to be
deploy-hiplingo-media:hiplingo-media-deploy and normally mode 0755 because
deployment rsync normalizes public directories.

Validate:

    stat -c '%A %a %U:%G %n' \
      /var/www/hiplingo.com \
      /var/www/hiplingo.com/app \
      /var/www/hiplingo.com/published-media

Expected current production shape:

    /var/www/hiplingo.com
        root:hiplingo-media-deploy 3775

    /var/www/hiplingo.com/app
        root:hiplingo-app-deploy 2775

    /var/www/hiplingo.com/published-media
        deploy-hiplingo-media:hiplingo-media-deploy 0755

======================================================================
9. TRANSFER TIMEOUT
======================================================================

The long-running rsync transfer has a 60-minute default timeout.

Optional override:

    PUBLISHED_MEDIA_RSYNC_TIMEOUT_MS

Example for a deliberately longer transfer:

    PUBLISHED_MEDIA_RSYNC_TIMEOUT_MS=7200000 \
    npm run deploy:published-media -- \
      --profile production \
      --plan-fingerprint <CURRENT_PRODUCTION_PLAN_FINGERPRINT> \
      --confirm DEPLOY_PUBLISHED_MEDIA

The override is milliseconds and must be at least 60000.

The initial ~157.8 MiB production upload exceeded the earlier hard-coded
10-minute limit, which is why the normal default is now 60 minutes.


======================================================================
10. WHAT THE ATOMIC DEPLOYMENT PROTECTS
======================================================================

Operational intent:

    1. create incoming sibling
    2. rsync package into incoming sibling
    3. checksum/difference verification
    4. swap staged tree into live published-media
    5. verify resulting state
    6. retain/restore the previous tree when required by failure handling

A failure during the initial rsync should not expose a partially copied live
media tree.

Observed during commissioning:
    - permission-denied failure left live published-media empty
    - transfer-timeout failure left live published-media empty
    - no abandoned incoming tree remained after the failed attempt

Do not bypass this by manually rsyncing directly into the live directory
during ordinary operation.

======================================================================
14. NGINX MEDIA ROUTE
======================================================================

Production nginx:

    location = /media {
        return 301 /media/;
    }

    location /media/ {
        alias /var/www/hiplingo.com/published-media/;
        autoindex off;
    }

Wrong:
    https://hiplingo.com/published-media/catalog.json

Correct:
    https://hiplingo.com/media/catalog.json

A wrong /published-media/... request can be captured by the SPA fallback and
return text/html. That is not successful media delivery.


======================================================================
15. TROUBLESHOOTING — ATOMIC STAGING PERMISSION DENIED
======================================================================

Symptom:

    rsync: [Receiver] mkdir
    "/var/www/hiplingo.com/published-media.metadata-editor-incoming...."
    failed: Permission denied (13)

Cause:
    deploy-hiplingo-media can write inside published-media but cannot create a
    sibling under /var/www/hiplingo.com.

Correct parent:

    root:hiplingo-media-deploy 3775

Correction:

    sudo chgrp hiplingo-media-deploy /var/www/hiplingo.com
    sudo chmod 3775 /var/www/hiplingo.com

Ensure live published-media is owned by deploy-hiplingo-media when a
sticky-parent atomic rename is required. Then rerun the sibling probe.


======================================================================
16. TROUBLESHOOTING — RSYNC TIMEOUT
======================================================================

Historical symptom:

    Error: rsync timed out after 600000ms.

That was the old 10-minute transfer ceiling.

Current metadata-editor:
    default long-transfer timeout = 60 minutes
    optional PUBLISHED_MEDIA_RSYNC_TIMEOUT_MS override

Before retrying, verify no rsync remains active:

    ps -ef | grep "[r]sync" || true

and inspect any incoming staging directory before starting a second write.


======================================================================
17. TROUBLESHOOTING — WFP RETURNS HTTP 403
======================================================================

Symptom:
    waveform-peaks.wfp -> HTTP 403

Typical nginx evidence:
    open() ".../waveform-peaks.wfp" failed (13: Permission denied)

If the PUBLIC WFP is 0600, nginx cannot read it because www-data is purposely
not in the media deployment group.

Emergency correction for already-deployed public WFP files:

    sudo find /var/www/hiplingo.com/published-media \
      -type f -name 'waveform-peaks.wfp' \
      -exec chmod 0644 {} +

Then verify the source-side publication/deployment permission fix is present.
A server-only chmod is not sufficient for future syncs.


======================================================================
18. TROUBLESHOOTING — MEDIA URLS RETURN SMALL HTML
======================================================================

If unrelated media URLs all return text/html with the same small length, the
request probably used /published-media/... instead of /media/... and fell
through to the SPA index fallback.

Use:
    https://hiplingo.com/media/...

Do not add a second nginx route merely to accommodate the wrong client URL.


======================================================================
19. ROUTINE MEDIA UPDATE WORKFLOW
======================================================================

For every future publication change:

    1. Make metadata/public-selection changes in metadata-editor.
    2. Regenerate/update the Web Package.
    3. Confirm only intended releases/tracks/videos are public.
    4. Run npm run audit:public-v1.
    5. Require Status: ready.
    6. Generate production plan with --profile production.
    7. Review add/update/remove/metadata counts and paths.
    8. Use the exact CURRENT production plan fingerprint.
    9. Execute the guarded production deployment.
   10. Regenerate the production plan.
   11. Require Status: current and 0 changes.
   12. Run the permission audit.
   13. Run public HTTP smoke tests.
   14. Spot-check Hiplingo frontend/browser behavior as appropriate.

Never let a media refresh become an implicit frontend deployment.
